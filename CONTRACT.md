# Factory Contract — config schema, driver ops, required keys and models

> `{plugin}` = root of the `factory` plugin: in commands it is `${CLAUDE_PLUGIN_ROOT}`; in workers it comes in the
> orchestrator's prompt as `Plugin: <path>`.

## Output language

The plugin's instructions are written in English. Every artifact, tracker comment, MR/PR comment and
user-facing message is written in `config.language` (e.g. `pt-BR`, `en`); if the key is absent, fall back to
the language the user is writing in.

---

Every factory command talks to the issue tracker **only** through these abstract operations.
No command knows whether it is Jira, GitLab, a CRM, etc. — it calls the operation and the **driver**
(selected by `config.tracker.driver`) translates it into the real call.

> **Golden rule:** if you are editing a *command* to support a tracker, you are doing it wrong.
> New tracker = **new `drivers/trackers/<name>.md`** + `tracker.driver: <name>` in the config. Nothing else.

---

Fixed text that commands and drivers write into the tracker or the code host (titles such as
`[Initiative] …`, `[QA Auto] …`, `Related bug: #n`, `Depends on #n`, table headers, comment headings) is a
**template**: render it in `config.language` too. Identifiers stay as they are: labels, status values, branch
names, `STATUS:` values and config keys.

## Substitution grammar (how the command reads the config)

- **Project root:** relative paths (`docs/factory.config.md`, `docs/initiatives/`, a Markdown board) are relative
  to the current directory, unless the prompt carries `Project root: <path>` (used by `/factory:demo`).

- `{config.<dotted.path>}` — e.g. `{config.git.base_branch}`.
- Keyed maps: `{config.workspace.repos.backend.path}` (repos is a **map** `backend|frontend`, not a list).
- **Forbidden** to leave a literal placeholder in the output. If a key is absent or has the value
  `TBD`, the command **STOPS** (see "Required keys").
  When stopping, **show the line's comment** if there is one (`# suggestion: ...` / `# weak candidate: ...`,
  generated by `/factory:init`) — the human confirms and fills it in instead of investigating from scratch.

## Logical names (resolved via config, never hardcoded in the driver)

- **Logical statuses:** `backlog`, `in_progress`, `qa_gate`, `in_qa`, `done` → `config.tracker.status.<logical>`
  (full lifecycle: PO creates in `backlog` → DEV moves `backlog`→`in_progress`→`qa_gate` → QA moves `qa_gate`→`in_qa`→`done`).
  `backlog`/`in_progress` are only required for the DEV factory; `qa_gate` is the DEV→QA **handoff point**.
- **Logical statuses of the CR factory** (MR/PR code review): `review_gate` (task ready for CR — entry),
  `in_review` (CR in progress), `review_approved` (approved → **advances**), `review_returned` (rejected → **returns**)
  → `config.tracker.status.<logical>`. `review_gate` and `in_review` MUST be distinct selectors (same rule as
  `qa_gate`×`in_qa`). Only required for the CR factory.
- **Logical labels:** `approved`, `auto`, `generated`, `needs_human`, `upstream_bug` → `config.tracker.labels.<logical>`
- **Issue types:** `bug` | `story`

### Status resolution (critical rule)
`config.tracker.status.<logical>` resolves to a **backend selector**, whose shape depends on the driver:

| driver | selector shape | example |
|--------|----------------|---------|
| jira | status name (string) | `qa_gate: "PR"` |
| gitlab | `{ state: opened\|closed, label?: <stage> }` | `qa_gate: {state: opened, label: ready-for-qa}` |
| github | `{ state: open\|closed, label?: <stage> }` | `qa_gate: {state: open, label: ready-for-qa}` |
| markdown | `{ folder: <folder>, label?: <stage> }` | `in_qa: {folder: em-qa, label: qa-iniciada}` |

**RULE:** `qa_gate` and `in_qa` **MUST** resolve to **distinct** selectors (distinct name, or
same state/folder + distinct label). Collapsing both into the same value is forbidden — otherwise the
STEP 0 gate cannot tell "ready for QA" from "already in QA" and re-runs a task in progress.
In `fetch`, the driver returns the logical status by the **most specific** selector that matches (the one with a label wins).

## Operations (the ones the QA factory uses)

| # | Operation | Input | Output / Effect |
|---|-----------|-------|-----------------|
| 1 | `fetch(id)` | id | `Task{ id, title, type, logical_status, parent_id?, branch?, linked_mr?, description, assignee? }` |
| 2 | `read_blueprint(id)` | id | spec/blueprint. **Default = `fetch().description`**; separate op only if the spec lives outside the description |
| 3 | `transition(id, target)` | id, **logical** status | moves the issue to the selector of `config.tracker.status[target]` (changes state/folder and/or label, removing conflicting stage labels) |
| 4 | `comment(id, md)` | id, markdown | adds a comment (driver converts markdown→backend format) |
| 5 | `create_child_bug(task, title, md)` | **id of the task in QA**, title, body | creates a bug **linked to the task** ("relates/linked" relation, NOT a child of the epic) → returns `new_id` |
| 6 | `label(id, target)` | id, **logical** label | applies `config.tracker.labels[target]` |

**`branch`/`linked_mr`:** `fetch` MUST return the task's dev branch (the pipeline does `diff`/`pull`).
Each driver declares how it resolves it (a convention like `{prefix}{id}`, a linked MR, or a field on the card).
⚠️ When the branch is **not** derivable from the key (e.g. ClickUp with branch `CU-{clickup_id}`), the driver reads it from the
appropriate field — the command never assumes `{prefix}{id}`.

> Ops of other commands (outside the pilot): `assign`, `query_backlog`. Same pattern.

## Authoring ops (PO factory — `po-tasks`)

`po-tasks` creates Epic + Stories in the tracker through these ops. The driver translates: **markdown** = files
on the kanban (`board_path`); **gitlab/github/jira** = Issues on the server.

| # | Operation | Input | Output / Effect |
|---|-----------|-------|-----------------|
| A | `create_epic(slug, title, body, meta)` | slug, title, body, `{labels}` | creates the epic/initiative → `epic_ref` |
| B | `create_story(title, body, meta)` | title, body (= full blueprint block), `{epic_ref, depends_on[], labels[], complexity, priority}` | creates the story (type=story) linked to the epic → `story_ref` (includes `id`) |
| C | `link_dependency(story_ref, depends_on_ref)` | two refs | records the **reciprocal** dependency (markdown: `blocks[]`/`depends_on[]`; gitlab/jira: relates/blocks link; github: native "blocked by") |
| D | `update_epic(epic_ref, stories[])` | epic + list of stories | updates the stories index/table in the epic |

**How the driver resolves id and location:**
- markdown → sequential id via `issue.id_format` (scans `board_path` for the highest number); writes to
  `tracker.epic_folder` (epic) and `tracker.story_folder` (stories).
- gitlab/github/jira → id assigned by the server; writes to `project_path`/`repo`/`project_key`; native issue links.

**Required keys of the PO factory (validate in STEP 0 of `/factory:po`):**
`product.{domain,personas}` (+ `competitors`/`compliance` when the domain requires it) — researcher;
`docs_map.codebase` — codemap; `stack.{backend,frontend}` — blueprint;
tasks: markdown→`tracker.{board_path,epic_folder,story_folder}` + `issue.id_format`; gitlab→`project_path`; github→`tracker.repo`.

## Required keys of the DEV factory (validate in STEP 0 of `/factory:dev`)
`tracker.status.{backlog,in_progress,qa_gate}` (distinct!); `git.{dev_base,protected,branch_prefix,commit_format,remote}`;
`workspace.{root,repos}`; `stack.{backend,frontend}.build`; `docs_map.codebase`;
`dev.{developer_split,doc_sync_order,retries,commit.{by,push}}`. Optional: `dev.self_test.pre_migrate_stash`,
`stack.frontend.lint`, `tests.seeder`.

> **`git.dev_base` ≠ `git.base_branch`:** the DEV factory creates the branch from `git.dev_base` (e.g.
> branch off `origin/beta`); QA diffs against `git.base_branch` (e.g. `origin/dev`). If they coincide
> (PHCS: both `develop`) → repeat the value; do not assume they are equal.

> **Transition in DEV:** `/factory:dev` uses `tracker.transition` with `in_progress` (on start) and `qa_gate`
> (handoff to QA). No new driver op — `transition` already covers it (they are just more logical statuses).

## SCM axis (code host) — CR factory

The task lives in the **tracker**; the MRs/PRs live on the **code host** (SCM). They may be different systems
(e.g. task in **ClickUp** + MR on **GitLab**). That is why the CR factory has a **2nd axis**:
the SCM driver in `config.scm.driver` translates the MR ops below (files in `drivers/scm/<name>.md`).
When tracker and code host are the same system (e.g. PHCS = GitLab Issues + MR), `scm.driver` may
point to the same backend — they remain separate axes in the config.

> **Same golden rule:** new code host = **new `drivers/scm/<name>.md`** + `scm.driver: <name>`. No command changes.

| # | Operation | Input | Output / Effect |
|---|-----------|-------|-----------------|
| S1 | `find_mrs(task)` | `Task` (from `fetch`) | list of open MRs with `target == config.scm.mr_target`. Sources: (a) URLs/refs in `task.description` + comments; (b) **fallback** by the branch convention `config.scm.branch_convention` (scans `config.scm.repos`). Excludes the twin branch `config.scm.exclude_branch_suffix`. → `[{repo, iid, url, source_branch, target_branch, state, title}]` |
| S2 | `mr_view(repo, iid)` | repo, iid | metadata + `state` (open/merged/closed). CR only runs on `open`. |
| S3 | `mr_diff(repo, iid)` | repo, iid | unified diff of the MR (vs merge-base with the target). **Read-only — never checks out** (does not change the local branch). |
| S4 | `mr_comment(repo, iid, md)` | repo, iid, markdown | posts a comment/note **on the MR itself** (≠ the tracker's `comment`, which is on the task). |

**Required keys of the CR factory** (validate in step 0; missing/`TBD` → STOP):
`tracker.driver`; `tracker.status.{review_gate,in_review,review_approved,review_returned}` (review_gate≠in_review);
`scm.driver`; `scm.repos` (map); `scm.mr_target`; `scm.branch_convention`; `workspace.root`;
`stack.{backend,frontend}` (only what the project has — derives the review checklist); `docs_map.codebase` (detect duplication).
Optional: `scm.exclude_branch_suffix`; `tracker.labels.{approved,needs_human}`.

## E2E axis (frontend test tool) — QA factory

What changes between Cypress, Playwright and other tools (test syntax, login, waiting, selectors,
evidence, execution and result format) lives in an **E2E driver** in `drivers/e2e/<name>.md`. The
`qa-frontend` and `qa-runner` workers do not know the tool: they follow the driver.

**Selection:** `<name>` = first word of `config.stack.frontend.e2e` in lowercase (`"Playwright 1.5x"` →
`playwright`). Key absent → `cypress` (compatibility). Driver file does not exist → **STOP**
("create `drivers/e2e/<name>.md`").

> **Same golden rule:** new tool = **new `drivers/e2e/<name>.md`** + `stack.frontend.e2e`. No worker changes.

| # | Driver section | What it declares |
|---|---|---|
| E1 | `files` | test file extension and layout; how to group (suite) and declare 1 test with the scenario ID in its name |
| E2 | `auth` | **programmatic** login per role (no form) and cleanup via API; where the project's helpers live (`config.tests.frontend_cmds`) |
| E3 | `wait` | how to wait for UI state with an **assertion with timeout** (never a fixed sleep) |
| E4 | `selectors` | selector preference order and the fallback; how to flag an unstable selector |
| E5 | `evidence` | how to enable video, screenshot on failure, *slow motion* and resolution from `config.evidence.*` |
| E6 | `run` | how to run only the feature's tests and how to recognize in the log what ran |
| E7 | `result` | format of the file in `evidence.artifacts.frontend_result` and how to extract total, passed, failed and, per failure, name, message and artifacts |

---

## What every driver MUST declare
1. **`Config keys`** it reads. 2. **`Capabilities`** + **fallback** when there is no native equivalent
   (e.g. no sub-issue → sibling bug + link). 3. **Access prerequisite** (MCP/CLI/API).

## Minimum viable
Serves any tracker that fulfills the 6 ops (with an acceptable fallback) **and** has programmatic means
(MCP/CLI/API). `qa_gate` and `in_qa` must be **distinctly representable** — if the backend has no
native statuses, use a discriminating **label/stage** declared in the config.

---

## Required keys of `factory.config.md` (validate in step 0; missing/`TBD` → STOP)
`project`, `company`, `tracker.driver`, `tracker.status.{qa_gate,in_qa,done}` (distinct!),
`tracker.labels.approved`, `issue.id_regex`, `git.base_branch`,
`workspace.root`, `workspace.repos.{backend,frontend}.path`,
`tests.dir`, `tests.layout.{backend,frontend}`, `stack.backend.test`, `stack.frontend.e2e`,
`env.{app_url,api_url}`, `docker.run`, `docker.ensure_up`, `evidence.{mode_var,slowmo_var,slowmo,resolution}`,
`evidence.artifacts.{videos,screenshots,backend_result,frontend_result}`.
(Drivers require extra keys of their own: jira→`cloud_id,project_key`; markdown→`tracker.board_path`; github→`tracker.repo`.)

**Optional runner keys:** `docker.run_frontend` (present → back/front are separate commands run
in parallel; absent → `docker.run` is the full pipeline); `tests.smoke_script` (absent → smoke via login +
1 endpoint); `tests.seeder` (used in migrate/seed only when `docker.ensure_up: true`).

## Models per role (`models`, optional)

Each worker runs on a model resolved by the **orchestrator**, in this order (the first that exists wins):
1. `--model <role>=<value>` in the run's arguments (one-off override);
2. `config.models.<role>` in `factory.config.md`;
3. `config.models.default`, if ≠ `inherit`;
4. the **plugin default** (table below; for DEV agents it is the frontmatter `model:`).

The orchestrator passes the value in the `model` parameter when spawning each worker. **The orchestrator's own model
is not configurable** — it is the session's (`inherit`).

Valid values: `fable` · `opus` · `sonnet` · `haiku` · `inherit`. Alias only (tracks the newest version
of the model); any other value → **STOP** in STEP 0 saying which key.

| Level | Roles (`<factory>.<role>`) | Default |
|---|---|---|
| 1 — judgment | `dev.tech_lead`, `dev.code_reviewer`, `cr.security`, `po.blueprint`, `qa.planner` | `fable` |
| 2 — volume | `dev.developer`, `qa.backend`, `qa.frontend`, `po.researcher`, `po.codemap`, `cr.reviewer` | `opus` |
| 3 — mechanical | `dev.self_test`, `dev.doc_sync`, `qa.runner`, `po.tasks` | `sonnet` |

```yaml
models:                 # optional — omitted = table defaults
  default: inherit
  dev.developer: fable
  qa.runner: haiku
```
